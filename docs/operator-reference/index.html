Data Flow & Usage — Operator's Reference

The pipeline produces four deliverables — standalone HTML data visualizations and exploratory tools, one per downstream stage:

  • palette_explorer.html
  • archetype_distribution.html
  • drift_comparison.html
  • coverage_distribution.html

None of them can be built until the data_prep stage has extracted clustered color data from source images.

Deliverables can be built using a sequence of CLI commands.

Tunables are modifiable constants, keyword dictionaries, threshold files, etc… that influence output deliverables.

Legend

Solid arrows show data flow — each command reads the output file produced by the previous one. Dotted teal lines link a tunable to the command it configures.

data_prep

Runs once per brand, turning raw product images into clustered color data. Provides the data that feeds the four key deliverables.

◉ HERALDIC_KEYWORDS
  • Source: a Python list concatenating category sub-lists (product-type exclusions, generic terms, states, cities, colleges, countries, sports terms, and pro rosters — soccer/football/basketball/baseball/hockey) — data_prep/heraldic_filter.py

  • How to tune: discover-heraldic-keywords · validate-heraldic-filter

◉ BRAND_KEYWORD_MAPS
  • Source: a per-brand dict (title word → Fashionpedia class synonyms) — data_prep/keyword_maps.py
  • Role: picks which detected garment is the target. A title word (“hoodie”, “polo”) maps to a Fashionpedia class, and the largest YOLO mask of that class becomes the hero garment; a title with no mapped word drops the product. Recognition coverage ~80–98% by brand (98% Nike).
  • How to tune: validate-keyword-map
  • Tuning output: 📄 per-brand coverage % over denominator + a list of uncovered titles (mirrors the SQL regex-inversion behind the original 98% Nike figure)
◉ IOU_THRESHOLD = 0.15 / OVERLAP_RATIO_THRESHOLD = 0.1 fixed constant · ✋ manual
  • Source: float constants — data_prep/segment.py
  • Role: attribute-merge gate. Once the hero garment is chosen, each detected attribute (sleeve, collar, cuff, hood, pocket, zipper, …) or secondary garment is folded into the hero mask if its IoU with the hero box > 0.15 OR its overlap with the dilated hero mask > 0.1 — capturing contrasting sleeves/collars that are part of the garment's palette. Lower = more aggressive merging.
  • How to tune: no command — hand-judged. Read the per-product merge line (candidates evaluated / merged / Avg IoU / Avg Overlap) in processing_log.txt, compare the merged masks against the source images, adjust the constants, and re-run.
  • Tuning output: 📄 processing_log.txt (per-product merge counts + IoU/overlap averages), inside each segmentation output folder

◉ NUM_CLUSTERS = 5 fixed constant · ✋ manual
  • Source: int constant — data_prep/cluster.py
  • Role: dominant colors extracted per garment. K-means (k=5) runs on the garment's masked pixels in LAB space; the 5 centroids and their coverage % become that product's palette and feed every downstream deliverable. palette_explorer

palette_explorer.html — the headline deliverable: a single at-a-glance view of a brand's entire color distribution. Two HAC passes consolidate every product's dominant color into internally-coherent zones (ΔE = 8), group those into hue families, and an adaptive layout renders them as population-scaled circles in lightness-ordered rows.

◉ CLUSTER_THRESHOLD = 8
  • Source: int constant (CIEDE2000 ΔE diameter) — palette_explorer/build_color_clusters.py
  • Role: HAC Pass 1 diameter: products within ΔE = 8 (CIEDE2000) form one cluster. Intentionally tight (over-discriminative) to keep clusters pure where dissimilar colors sit close; the resulting over-segmentation is corrected downstream by zone merging.
  • How to tune: Iterative human-review loop. Run consolidate-colors <brand> --gender <g> to build clusters at the current value, then review-cluster-quality <brand> --gender <g> to render that same segment for inspection. Adjust the constant and re-run both until clusters hold together by eye.
  • Tuning output: A self-contained HTML page at outputs/diagnostic_cluster_review/<brand>_<gender>/cluster_review.html — one tab per cluster, each showing that cluster's 20 most color-diverse products (farthest-point CIEDE2000 sample, chosen to surface misfits).

Tunables
◉ cluster_zones.json
  • Source: the hand-built reference file outputs/nike_mens/cluster_zones.json — cluster→zone assignments created via build-zones. (The ~9 files assign-zones writes for other segments are its outputs, not this tunable.)
  • Role: HAC Pass-1 clusters are deliberately over-discriminative; zones merge the near-identical ones into human-meaningful groups. assign-zones trains a Random Forest on the reference labels and propagates that merging to the remaining ~9 brand/genders.
  • How to tune: hand-label nike/mens once — build-zones nike --gender mens → label in the tool → export — then assign-zones <b> <g> propagates it to the other ~9 segments. (To use a different segment as ground truth, change TRAINING_BRAND / TRAINING_GENDER in palette_explorer/assign_zones.py.)
  • Tuning output: cluster_zone_builder.html (the labeling tool)
◉ CONFIDENT_MERGE_PROB = 0.80
  • Source: float constant CONFIDENT_MERGE_PROB = 0.80 — palette_explorer/assign_zones.py. (scipy's linkage merges on distance, so the code derives 1 − 0.80 = 0.20 inline at the merge step — there's no separate distance constant.)
  • Role: the RF scores each pair of target clusters with a “same-zone?” probability; agglomerative complete-linkage merges only pairs it's ≥ 80% confident about. Higher = stricter (more, smaller zones); lower = looser (fewer, broader zones).
  • How to tune: run assign-zones nike --gender mens (self-validation). Read the printed ARI/NMI agreement scores; if they're too low, use the Manual-zones vs Auto-zones counts to see whether the RF is over-merging (fewer auto zones) or under-merging (more), adjust CONFIDENT_MERGE_PROB, and re-run until the scores plateau — before propagating to the other segments
  • Tuning output: auto_cluster_zones.json (the RF's version, saved for optional cluster-level inspection — the tuning decision is read from the console ARI/NMI)

archetype_taxonomy

archetype_distribution.html — classifies each product by color structure into one of five archetypes (MONO, DOM_ACC, DUAL_BAL, MULTI_DOM, MULTI_BAL) from how many significant color clusters survive merging and how dominant they are, then reports the mix across the brand (≈92% of the catalog is single-color).

Tunables
◉ archetype thresholds
  • Source: five module-level constants in archetype_taxonomy/classify_archetypes.py — DOMINANCE_RATIO=2.0 (:82), SECONDARY_COVERAGE_THRESHOLD=10 (:87), and the hue-aware significance triple SIGNIFICANCE_THRESHOLD_OPPOSITE_HUE=1 (:77), SIGNIFICANCE_THRESHOLD_DIFFERENT_HUE=3 (:78), SIGNIFICANCE_THRESHOLD_SIMILAR_HUE=5 (:79). They're read directly by filter_significant_clusters() (:204) and classify_structure() (:258); no CLI override, edit the constants.
  • Role: Post-merge, the classifier walks a two-step decision tree on each product's merged palette. First filter_significant_clusters() keeps only colors whose coverage beats a hue-dependent significance floor — a color whose hue is >90° from the dominant needs ≥1% coverage to count, >45° needs ≥3%, similar hue needs ≥5% (:242-250). Then classify_structure() labels the surviving palette: 1 color → MONO; 2 colors with ratio ≥ DOMINANCE_RATIO → DOM_ACC else DUAL_BAL; 3+ colors with combined secondary coverage < SECONDARY_COVERAGE_THRESHOLD → DOM_ACC (tiny accents), else MULTI_DOM if dominant ≥ 50% else MULTI_BAL (:293-300).
  • How to tune: run archetype-review to draw (or reuse) a stratified validation sample and render the browser labeling tool; hand-label archetype and merge, export from the tool as validation_results_hsb.csv, then run validate-archetypes to score. Reuse is the default — the sample is redrawn only with --resample, so the labels you already have aren't orphaned by an accidental rebuild (review_archetype_labels.py:16-20). Adjust the constants, re-run archetypes, re-open the tool (regenerated cheaply every review), re-validate.
  • Tuning output: archetype_taxonomy/outputs/archetype_validation.html (the labeling tool — one row per sampled product, buttons for the archetype guesses, a merge-labeling panel) and archetype_taxonomy/outputs/archetype_accuracy.txt (the validate-archetypes report — overall accuracy with a Wilson 95% CI, 5-class confusion matrix, per-class precision/recall/F1, and the top misclassification flows, validate_archetype_classification.py:248-251).

◉ N_CLUSTERS = 1900 fixed constant · ✋ manual
  • Source: int constant — drift/downsample.py:14
  • Role: archive compression — how far archives are compressed before drift
  • How to tune: no command — edit N_CLUSTERS by hand at drift/downsample.py:14 and re-run downsample + compute-drift for the affected brand(s). † shared tunables

Some tunables configure more than one stage. They're documented once here; the stages that use them link back to this section.

Tunables
◉ hue-merge rule
  • Source: int constants in shared/palette_merge/palette_merge.py — HUE_MERGE_THRESHOLD = 25° (max hue gap to merge two chromatic colors), LOW_CHROMA_MERGE_THRESHOLD = 15 (chroma below which a color counts as low-chroma/near-neutral), LOW_CHROMA_MAX_DELTA_L = 35 (the lightness guard), plus NEUTRAL_CHROMA_THRESHOLD = 8 (chroma below which a color has no usable hue). Shared — the same merge primitive also builds the palettes the archetype classifier consumes, so changing it moves two deliverables.
  • Role: per-product merge that runs before HAC Pass 1. For each product it collapses colors that are just lighting artifacts (highlights/shadows) into one and keeps the dominant survivor as that product's color for clustering. Two low-chroma/neutral colors merge only if their lightness is within LOW_CHROMA_MAX_DELTA_L (35) — this keeps black+white from collapsing together; two chromatic colors merge if their hue is within HUE_MERGE_THRESHOLD (25°), with no lightness guard — which is why navy over-merging into royal blue is a known, unfixed limitation, not something these thresholds prevent.
  • How to tune: data-driven, then by hand.
    ① Build the labeling tool: run archetype-review --strata pair-features — one command that classifies (if needed), draws a boundary-oversampled sample (deliberately loaded with color pairs sitting near the hue/chroma/ΔL thresholds, which fits merge-rule tuning far better than the default archetype-stratified sample), and renders archetype_validation_pairfeatures.html (separately named so it can't clobber an archetype-accuracy sample). The default --strata archetype also captures merge labels in passing, but under-samples the ambiguous pairs this decision hinges on.
    ② Label: open that page and click each color swatch to cycle it into the right group (which of a product's colors are really the same); export merge_labels_all_brands.csv.
    ③ Fit + apply: run tune-merge-rules --input merge_labels_all_brands.csv --propose-constants — it scores the live merge rule against your labels and proposes new values in the shape of the constants (e.g. HUE_MERGE_THRESHOLD 25 → 27, acc 94.7% → 95.1%) with a cross-validation guard. Edit the constants by hand in palette_merge.py; the tool never writes them.
  • Tuning output: outputs/merge_rule_discovery/ — the proposals (merge_constant_proposals.txt, merge_constant_sweep.csv), decision-boundary HTML plots (labeled pairs against hue-difference and ΔL), and pairwise_features.csv. Adding --fit-tree instead also writes a decision tree (merge_rules_discovered.txt).

Docker usage

Docker is the intended path — the container ships with the CUDA stack, the Python dependencies, and the right paths for images and outputs. Every cli.py <command> <args> invocation in this document translates to the same wrapper.

One-time setup

cd color-analytics
docker compose build

Then, once per PowerShell session:

$env:POSTGRES_PASSWORD = "<your db password>"

DB_HOST is already wired to host.docker.internal in docker-compose.yml:13, so no host configuration is needed if your database runs on the machine you're running Docker on. POSTGRES_PASSWORD is not declared in the compose file's environment: block, so it has to be forwarded explicitly on each run (see the translation rule).

The translation rule

Everywhere in this document you see

cli.py <command> <args>

run it from the color-analytics directory as

docker compose run --rm -e POSTGRES_PASSWORD=$env:POSTGRES_PASSWORD `
    pipeline python cli.py <command> <args>

--rm removes the container after the command exits, so repeated runs don't leave a graveyard of stopped containers behind. The backtick at the end of the first line is PowerShell's line continuation — write it as one line if you prefer.

What the compose file already handles for you

  • The repo is mounted at /app, so anything written to outputs/… inside the container appears in color-analytics/…/outputs/ on the host.
  • Product images are mounted at /app/images from the sibling 03_images/ tree (docker-compose.yml:11).
  • GPU access is passed through (docker-compose.yml:20-24) — required for segment (YOLO inference) and compute-drift (CUDA Sinkhorn).

Two worked examples

Brand-required stage:

docker compose run --rm -e POSTGRES_PASSWORD=$env:POSTGRES_PASSWORD `
    pipeline python cli.py segment nike

Multi-brand deliverable:

docker compose run --rm -e POSTGRES_PASSWORD=$env:POSTGRES_PASSWORD `
    pipeline python cli.py archetypes

Running without Docker

If you have the CUDA + Python stack installed locally, the same python cli.py <command> <args> works from color-analytics with $env:POSTGRES_PASSWORD and $env:DB_HOST set in your shell. Docker is the default because reproducing that stack from scratch is the harder half of the setup.
